# 对象存储、备份与恢复

> 适用：`sometable.com` 生产环境（`/www/apps/sometable`，Docker Compose）。
> 最后更新：2026-11-21

## 1. 为什么后台没有「对象存储设置」页面

文件存储属于**部署级配置**，不是普通用户或工作区设置，因此 Baserow 系系统把它放在**环境变量**里，而不是管理界面：

- 修改位置：项目根目录的 `.env` 文件（以及 `docker-compose.yml` 中的环境变量透传）。
- 修改后需要重建/重启容器才生效：`sudo -n env BASEROW_VERSION=... docker compose up -d`。
- 管理后台只显示版本等信息，不提供存储配置入口，这是上游设计。

## 2. 文件默认存放在哪里

### 2.1 未配置对象存储（默认）

| 项 | 值 |
| --- | --- |
| 容器内路径 | `/baserow/media`（`MEDIA_ROOT`） |
| Docker 卷 | `sometable_media` |
| 宿主机实际路径 | `/www/docker/volumes/sometable_media/_data` |

所有用户上传（附件字段文件、图片、导出中转文件、模板 zip 等）都在这个卷里。数据库本身在卷 `sometable_pgdata`。

### 2.2 已配置 S3 / S3 兼容对象存储

当 `.env` 里设置了 `AWS_STORAGE_BUCKET_NAME` 时，上传文件直接写入对象存储，本地 `media` 卷基本为空。相关变量：

```bash
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
AWS_STORAGE_BUCKET_NAME=
AWS_S3_REGION_NAME=
AWS_S3_ENDPOINT_URL=        # MinIO / Cloudflare R2 / 阿里云 OSS 等兼容服务
AWS_S3_CUSTOM_DOMAIN=       # 可选，CDN 域名
AWS_LOCATION=               # 可选，桶内前缀
AWS_QUERYSTRING_AUTH=
AWS_DEFAULT_ACL=
AWS_S3_ADDRESSING_STYLE=
```

判断当前实际使用的是哪一种：

```bash
cd /www/apps/sometable
grep -c '^AWS_STORAGE_BUCKET_NAME=.\+' .env          # >0 表示已启用对象存储
sudo -n du -sh /www/docker/volumes/sometable_media/_data
```

> **当前生产实例已配置对象存储**（`.env` 中存在 `AWS_STORAGE_BUCKET_NAME` 与 `AWS_S3_ENDPOINT_URL`）。因此备份时**必须同时备份对象存储桶**，只备份数据库会丢失附件。

## 3. 备份

### 3.1 一键备份脚本

脚本：`docs/deployment/scripts/backup-sometable.sh`
输出目录：`/www/backups/sometable/<时间戳>/`

包含：

| 文件 | 内容 |
| --- | --- |
| `database.dump` | PostgreSQL 逻辑备份（`pg_dump -Fc`，可被 `pg_restore` 恢复） |
| `media.tar.gz` | 仅在使用本地 `media` 卷时生成 |
| `manifest.txt` | 时间、版本、文件大小、校验和、存储类型 |

执行：

```bash
cd /www/apps/sometable
sudo -n bash docs/deployment/scripts/backup-sometable.sh
```

保留策略：默认保留最近 7 份（`KEEP=7` 可覆盖）。

### 3.2 定时备份

推荐用 root 的 cron（每天 03:30）：

```bash
sudo -n crontab -e
# 添加：
30 3 * * * cd /www/apps/sometable && /bin/bash docs/deployment/scripts/backup-sometable.sh >> /var/log/sometable-backup.log 2>&1
```

> 备份会短暂增加数据库 IO，但使用 `pg_dump` 不会锁表，不影响正常使用。

### 3.3 对象存储桶的备份

对象存储不在本机，无法用上面的脚本打包，需要在对象存储侧配置：

- 开启**版本控制（Versioning）**；
- 配置**生命周期规则**（例如保留 30 天历史版本）；
- 或使用 `rclone` / `aws s3 sync` 定期同步到另一个桶：

```bash
rclone sync remote:sometable-media remote:sometable-media-backup --progress
```

### 3.4 手动最小备份（不依赖脚本）

```bash
cd /www/apps/sometable
mkdir -p /www/backups/manual
# 数据库
sudo -n docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > /www/backups/manual/database.dump
# 本地媒体（若未使用对象存储）
sudo -n docker run --rm -v sometable_media:/mnt:ro busybox tar czf - -C /mnt . > /www/backups/manual/media.tar.gz
```

## 4. 从备份恢复

> 恢复会覆盖现有数据。务必先停掉写入方，并确认备份文件完整。

### 4.1 停止应用（保留数据库容器）

```bash
cd /www/apps/sometable
sudo -n docker compose stop web-frontend backend celery-export-worker celery-beat-worker celery
```

### 4.2 恢复数据库

```bash
sudo -n docker compose exec -T db sh -c 'dropdb -U "$POSTGRES_USER" --force --if-exists "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
sudo -n docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --clean --if-exists' < /www/backups/sometable/<时间戳>/database.dump
```

### 4.3 恢复本地媒体（仅本地存储模式）

```bash
sudo -n docker run --rm -i -v sometable_media:/mnt busybox sh -c 'rm -rf /mnt/* && tar xzf - -C /mnt' < /www/backups/sometable/<时间戳>/media.tar.gz
```

使用对象存储时，改为在对象存储控制台把桶/前缀回滚到备份时间点（依赖版本控制或镜像桶）。

### 4.4 启动并校验

```bash
sudo -n env BASEROW_VERSION="$(grep '^BASEROW_VERSION=' .env | cut -d= -f2)" docker compose up -d
sudo -n docker compose restart caddy
for p in / /login/ /api/_health/ /api/settings/; do
  curl -sS -m 10 -H 'Host: sometable.com' -o /dev/null -w "$p %{http_code}\n" "http://127.0.0.1:8088$p"
done
```

预期：`/` 302，其余 200；`docker compose ps` 全部 healthy。

### 4.5 恢复到另一台机器

1. 部署同一版本的镜像（`.env` 的 `BASEROW_VERSION` 保持一致）；
2. 按 4.2 恢复数据库；
3. 按 4.3 恢复媒体，或在 `.env` 指向同一个对象存储桶；
4. 修改 `BASEROW_PUBLIC_URL` / 域名与证书后启动。

## 5. 备份检查清单

- [ ] `database.dump` 大小正常（不是 0 字节）
- [ ] 使用对象存储时，桶已开启版本控制或有独立备份
- [ ] 定期做一次**恢复演练**（至少每季度），确认备份可用
- [ ] 备份目录 `/www/backups` 不在系统盘，且磁盘使用率低于 80%

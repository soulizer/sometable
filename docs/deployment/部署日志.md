## 4. 运行架构

```
浏览器
  │  HTTPS 443
  ▼
宝塔 Nginx（sometable.com.conf，TLS 终止 + 301 归一化）
  │  HTTP 127.0.0.1:8088
  ▼
Docker Compose: sometable-caddy-1 (Caddy :80)
  ├─ /api/* /ws/* /mcp ...  → sometable-backend-1 (Django, :8000)
  ├─ /media/*               → 媒体文件（本地卷）
  └─ 其余                    → sometable-web-frontend-1 (Nuxt, :3000)

附属服务：
  sometable-db-1        pgvector/pgvector:pg15
  sometable-redis-1     redis:6
  sometable-celery-1    异步任务
  sometable-celery-beat-worker-1     定时任务
  sometable-celery-export-worker-1   导出任务
```

## 5. 关键配置说明

### 5.1 镜像版本

仓库追踪 `develop` 分支，其后端迁移数量超前于 `2.4.3` 发布镜像（多 15 个迁移）。
因此此前设置 `BASEROW_VERSION=develop-latest`。

第 1 轮的源码改造（去引导、语言收窄、品牌替换）无法通过官方镜像生效，
因此第 2 轮改为**本地构建镜像**并打上日期标签：

```
BASEROW_VERSION=local-20261120-1548
```

- 构建命令：
  `docker compose -f docker-compose.yml -f docker-compose.build.yml build backend web-frontend`
- 每次改源码后需要重新构建并递增标签，滚动重启后才会生效。
- 回滚：把 `BASEROW_VERSION` 改回 `develop-latest`（或该日期之前的标签）后 `docker compose up -d`。

**构建注意事项（8 GB 内存机器）**

- 前端生产构建的 Nitro 打包阶段是最耗内存的一步。
  `web-frontend/config/nuxt.config.prod.ts` 默认**不生成 sourcemap**
  （需要时用 `NUXT_BUILD_SOURCEMAP=true` 打开），否则极易 OOM。
- 堆上限由 `web-frontend/Dockerfile` 的 `NODE_MAX_OLD_SPACE_MB`（默认 4096）控制。
- 构建前建议 `sudo docker builder prune -af` 清理缓存（曾积累 16.6 GB），
  否则 49 GB 的 `/www` 容易被写满。
- 构建耗时长，建议 `setsid nohup ... > /tmp/build.log 2>&1 &` 脱离会话执行。
- 容器重建后容器 IP 会变化，Caddy 会继续连旧 IP 导致 502，
  `docker compose restart caddy` 即可恢复。

### 5.2 对象存储

| 配置项 | 值 |
| --- | --- |
| endpoint | `https://s3.bitiful.net` |
| bucket | `drive` |
| region | `cn-east-1` |
| 前缀 `AWS_LOCATION` | `sometable` |
| 寻址方式 | path-style |

注意：该桶**不允许匿名读取**（不支持 bucket policy，对象 ACL 为 public-read 也无法匿名 GET）。
因此启用签名 URL：

```
AWS_QUERYSTRING_AUTH=true
AWS_QUERYSTRING_EXPIRE=604800
```

即所有文件链接都是 7 天有效期的预签名地址，随请求动态生成。

### 5.3 注册策略

- 实例设置 `allow_new_signups = false`：关闭公开注册。
- `show_admin_signup_page = false`：管理员已存在，前端显示登录页。
- 新用户只能通过工作区邀请加入。

### 2026-11-20 r3b5 构建资源事故与处置（重要）

- 现象：`local-20261120-r3b5` 前端构建在 Nitro 打包阶段（6m 后）停止输出，日志 1.5 小时无更新；内存 7.6G/7.8G 全占、Swap 4G 耗尽、可用内存 <120Mi，之后生产站点 `Host: sometable.com` 的 `/api/_health/` 超时不可用。`dmesg` 显示 `systemd-journald: Under memory pressure, flushing caches`。
- 原因：8 GB 机器上连续执行前端生产构建（r3b3 → r3b4 → r3b5 间隔过短），Docker 构建缓存 + Nuxt/Nitro 峰值叠加，可用内存与 swap 均被耗尽；构建进程进入长时间停滞（非正常退出）。
- 处置：`kill -9` 终止 `run-r3b5.sh`/`docker-compose build`/`nuxt build` 进程树 → 内存恢复（可用 3.3G、Swap 回落到 2.7G）→ 站点 `/api/_health/` 恢复 200。线上版本仍为 `local-20261120-r3b4`，无数据损坏（未执行部署步骤）。
- 结论与后续约束：
  1. **r3b5 不再重复构建部署**：其改动（邮件模板去营销、行评论门控清理、少量文案）属低可见度修复，已提交在 `e4162f515`，将在下一次**必要**构建时一并上线（与后续 3c 合并为一个批次），避免短间隔连续构建。
  2. 每次前端构建前必须：清理 Docker 构建缓存（`docker builder prune -af`）、确认可用内存 ≥3G、确认 swap 无大量占用、并保持单构建；构建期间不得再启动其他重任务。
  3. 构建必须有 `timeout` 与「日志停滞检测」：若日志超过 10 分钟无新增即判定异常并中止，避免拖垮线上服务。
  4. 若确需多次构建，先扩 swap（临时 8G）或分批隔天执行。

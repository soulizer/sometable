# 全站功能审计计划（2026-11-23 起）

> 目标：验证并修复整个系统的功能、权限、通知、文案与数据一致性，做到根因修复、同类覆盖。
> 原则：以实际代码为准；能复用现有组件/样式就不新造；每批「测试 → 修复 → 校验 → 提交 → 部署 → 记录」。

## 1. 测试环境与方法

- 环境：生产同源实例 `/www/apps/sometable`，`Host: sometable.com`，当前标签见 `当前构建标签.txt`。
- 后端：Django `manage shell` / `pytest`（APIClient），直接调用 service/handler，覆盖真实数据库。
- 前端：构建产物 + 运行时 i18n 负载（`/_i18n/.../messages.json`）核对；必要时用无头浏览器点击。
- 数据：新建独立测试工作区/用户/应用，命名前缀 `审计-`，不污染真实数据；测试结束按需清理或保留并标注。
- 邮件：只允许发送到 `access@126.com`；禁止向任何其它地址发信。
- 备份：每次大批量测试前生成备份；恢复演练使用副本，不动生产数据。

## 3. 可能冲突与回归范围

- 解锁门控（`hasFeature`/`isDeactivated`）改动会影响所有 premium/enterprise 入口，需回归“原本可用的核心功能”。
- 存储改为可配置后，所有文件读写路径（上传、导出、快照、模板、缩略图）都要回归。
- i18n 批量改动需回归英文回退与占位符。
- 权限改动需同时验证后端 permission manager 与前端显示。
- 迁移必须零停机：新增字段可空/有默认；旧后端短暂共存。

## 4. 通过标准

- 每个功能点在对应权限角色下行为与描述一致；无“未开放/升级”类残留提示。
- 后端接口对无权限用户返回 403/404，不泄漏数据。
- 通知在触发方与接收方一致（类型、目标、文案）。
- 中文界面无残留英文（技术标识除外）；同一概念术语一致。
- 备份可恢复：数据库 + 媒体/对象存储配置 + 应用数据完整。

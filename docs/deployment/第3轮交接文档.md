## 1. 项目与用户要求（原始需求，逐条执行）

这是一个基于 Baserow 二次开发的私有系统（对外域名 `sometable.com`，仓库内仍存在大量 `baserow` 内部标识）。用户提出第 3 轮四项要求：

### 1.1 彻底汉化
- 切换简体中文后**不允许残留英文**（技术标识如 `JSON`/`HTML`/`UUID` 除外）。
- 译文必须**准确、自然、贴合办公场景**，不能是生硬机翻。
- 用户明确点名的问题（仅举例，**所有同类问题都要修**）：
  - 行高选项：`Height` / `Small` / `Medium` / `Large` → 行高 / 紧凑 / 适中 / 宽松
  - 分组：`Group`、`You have not yet created any groupings`、`Group rows together by a field.`、`choose a field to group by`
  - 侧栏/导航：`All items`、`Dashboard`、`Automation`、`Create`、`Members`、`Settings`
  - 其他：图表名称、分享权限、审计日志等
- 用户要求"**主动发现未点名的问题**"，不能只改他举的例子。

### 1.2 全能力解锁
已实现但被 premium/enterprise 限制的功能必须**全部可用**，不允许出现"未开放/锁定/升级"提示：
- 仪表盘图表（bar / line / pie / doughnut）
- 分享选项（隐藏 logo、允许公开导出）
- 颜色调整、行/字段着色
- 看板 / 日历 / 时间线视图
- 日期依赖（date dependency）
- 视图归属 "To personal"
- 审计日志、数据扫描器
- 以及**所有同类限制**

若某能力"代码不存在"，需要评估并制定实现计划（按现有代码风格与成熟产品交互实现）。

### 1.3 去品牌 / 去非工具化
- 移除无意义的 `SomeTable` / `sometable` / `Baserow` 品牌展示。
- 左下角品牌不抢眼；侧栏折叠时**不能出现错误的 "S"**（保留原 icon 或不显示）。
- 模态窗、分享页等处不滥用 logo。
- 清理宣传、引导、营销、upsell、upgrade 弹窗与入口。
- 目标气质：**克制的办公工具**，不是营销产品页。

### 1.4 交付方式（硬性，务必遵守）
- **每个代码变更批次都必须 `git commit` 并 `git push` 到 GitHub。**
- **每个代码变更批次都必须构建并部署上线**，由用户直接在线上检查（用户**不看代码**）。
- 为控制资源，细粒度修复可合并为"可验收批次"，但**每批必须推送 + 必须部署**。

### 1.5 文档要求（硬性）
- **所有文档（临时或长期）一律写入项目 `docs/` 目录**（本轮主要在 `docs/deployment/`）。
- 禁止写到 `/tmp`、scratchpad 或其他位置（曾用 scratchpad，已被用户明确纠正）。

## 6. 构建与部署操作规程（务必严格遵守）

### 6.1 曾经的事故（必须避免重演）
`local-20261120-r3b5` 构建时：前端在 Nitro 打包阶段停滞，内存 7.6G/7.8G 全占 + swap 4G 耗尽 → **生产站点 `/api/_health/` 超时不可用**（`dmesg` 显示 `Under memory pressure`）。
处置：`kill -9` 构建进程树后恢复。**根因是短间隔连续构建**（r3b3 → r3b4 → r3b5 间隔太近），Docker 缓存 + Nuxt 峰值叠加。

### 6.2 正确做法：用 `run-r3bN.sh` 模板
参考 `docs/deployment/build-logs/run-r3b6.sh`（**成功案例**），复刻并改 `TAG`。它包含：

```bash
# 1) 构建前资源门槛（低于 2.5G 直接退出，不冒险）
avail_kb=$(awk '/MemAvailable/{print $2}' /proc/meminfo)
if [ "$avail_kb" -lt 2500000 ]; then exit 1; fi

# 2) 顺序构建，不并行；限堆 3072（不是 4096，8G 机器更安全）
sudo -n env BASEROW_VERSION="$TAG" NODE_MAX_OLD_SPACE_MB=3072 \
  docker compose -f docker-compose.yml -f docker-compose.build.yml build web-frontend

# 3) 每 30s 心跳 + 600s 日志停滞检测（无输出就判定卡死并 kill）
# 4) 两端构建都要 rc=0 才允许部署
# 5) up -d 后轮询 /api/_health/ 最多 180s 等就绪（刚重启 1 分钟内 502 是正常的）
# 6) 用 Host: sometable.com 做健康检查（否则 404，见 7.3）
```

**构建前必做**：
```bash
sudo -n docker builder prune -af       # 曾堆积 16.6GB 缓存把 /www 写满
df -h /www                              # 确认 ≥12G 可用
free -h                                 # 确认可用 ≥2.5G
```

**如需多次构建**：先临时扩 swap 到 8G，用完删除。不要把多次构建挤在 1 小时内。

### 6.3 部署（run 脚本已包含，手工等价命令）
```bash
cd /www/apps/sometable
cp .env .env.bak-<tag>-$(date +%Y%m%d%H%M%S)
sed -i "s/^BASEROW_VERSION=.*/BASEROW_VERSION=<tag>/" .env
sudo -n env BASEROW_VERSION=<tag> docker compose up -d
sudo -n docker compose restart caddy      # 必须！容器 IP 变了，caddy 会连旧 IP 导致 502
```
**注意**：`BASEROW_VERSION` 必须通过 `env` 传给 docker compose，否则 compose 会去拉 `docker.io/baserow/...:<tag>` 而失败（见 7.2）。

### 6.4 健康检查（唯一正确方式）
```bash
for p in / /login/ /api/_health/ /api/settings/; do
  curl -sS -m 10 -H 'Host: sometable.com' -o /dev/null -w "$p %{http_code}\n" "http://127.0.0.1:8088$p"
done
# 期望：/ 302，其余 200
```

### 6.5 回滚
改 `.env` 的 `BASEROW_VERSION` 为上一标签 → `up -d` → `restart caddy` → 复检。

## 7. 踩过的坑（不要重复踩）

### 7.1 `/www/baserow2` 不存在
历史文档提到过该目录，实际部署目录就是 `/www/apps/sometable`。

### 7.2 镜像标签不生效（compose 构建）
`docker compose ... build` 时 `BASEROW_VERSION` 必须放在 `sudo -n env VAR=... docker compose`，直接 `VAR=... sudo docker` 会丢失环境变量，导致镜像被打成旧标签或 `up -d` 去 registry 拉不存在的镜像。

### 7.3 用 127.0.0.1 访问会 404
Caddyfile 的 `@is_baserow_tool` 校验 `BASEROW_PUBLIC_URL`（`https://sometable.com`）是否包含 Host。用 `127.0.0.1` 做 Host 会 404/502。
**必须加 `-H 'Host: sometable.com'`**。曾因此误判"部署失败"。

### 7.4 Nuxt 构建完成但进程不退出
现象：日志出现 `Build complete` 然后 `process is still running: 1 open connection`，`docker compose build` 永不返回。
修复（已提交 `5ceead28e`）：`web-frontend/package.json` 的 build 脚本前加 `CI=1 NUXT_TELEMETRY_DISABLED=1`。**不要删除这两个变量。**

### 7.5 `.git/index.lock` 反复出现
并发执行 git 命令会残留锁。处理：`rm -f .git/index.lock` 再重试。**不要同时跑两个 git 写操作。**

### 7.6 `.env.bak*` 未被 gitignore
`.gitignore` 只忽略 `.env`，不忽略 `.env.bak*`。**提交时务必排除**，否则会把含敏感配置的备份推上去：
```bash
git add -A -- . ":(exclude).env.bak*"
```
（建议顺手把 `.env.bak*` 加进 `.gitignore`）

### 7.7 bash heredoc 解析 `$t('...')`
在 `python3 <<'PY'` 里用 shell 拼接 `$t(...)` 会触发 `SyntaxWarning: invalid escape sequence '\$'`，且结果不可靠。**直接在 Python 里写普通字符串，不要用 shell 双引号包 `$t`。**

### 7.8 不要用 explore 子代理查大范围后端
两次尝试 `explore` 子代理审查后端限制都因 turn limit 提前终止（消耗大量 token）。**用 `grep` 工具直接搜** 更快更准。

### 7.9 语言包 key 判断"是否已翻译"
用脚本对比 `en.json` 与 `zh_Hans.json` 的**扁平化 key**，值相同且含拉丁字母即为未翻译。本仓库已有现成做法（第 4.2 节的统计即由此得出）。

### 7.10 不要改 taste 文件
`.commandcode/taste/` 由系统管理，禁止手写。

## 11. 给接手的 AI 的额外提醒

1. **用户不看代码**，只看线上效果。所以"改完没部署"= "没做"。设备资源不允许时，先攒批次，但不要攒着不部署太久。
2. **不要过度设计**。这是私有系统的定制改造，不是给上游提 PR。删代码/写死返回值是被允许且用户明确要求的。
3. **不要回滚用户的数据**。数据库/媒体卷不要动；`docker compose down -v` 绝对禁止。
4. **改动前先 `read` 原文件**，此仓库大量文件名为 Baserow 遗留但逻辑已改，凭直觉改会出错。
5. **翻译质量**要求"像人写的办公软件中文"，不要出现"本系统"这类机械替换后的僵硬表述（曾批量把品牌名替换为「本系统」，部分长句读起来生硬，可顺手润色）。
6. 遇到构建卡住/资源耗尽，**先救服务**（kill 构建进程让内存回落），再记录事故，不要硬撑。
7. 每次进展都要写进 `第3轮进度与计划.md` 与 `部署日志.md`，这是跨会话唯一的记忆。
